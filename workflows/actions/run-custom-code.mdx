# Run Custom Code

> **Applies to:** Run Custom Code 1.0.0, 1.1.0, 1.2.0

The **Run Custom Code** action runs **JavaScript** or **Python** inside your workflow. Use it for logic that formulas cannot express: parsing complex JSON, multi-step transformations, or calls to an API that has no dedicated action yet. The code can call HTTP APIs, and from version 1.2.0 the integrations you attach to the step authenticate those calls for you.

<Note>Run Custom Code is available on paid plans.</Note>

<Tip>You don't need to write code from scratch. Click **Help me write code** in the code editor, describe what you want in plain language, and the AI assistant generates the code for you.</Tip>

## How the step works

1. **Data to use in the code**: name the values your code needs and map them to outputs of earlier steps. The code reads them from `inputData`.
2. **Integrations the code can call** (1.2.0 and later): attach the connected integrations the code may talk to. Each one gets an **alias**, a short name the code can use.
3. **Language** and **Code**: write the body of a function. Whatever you `return` becomes the output of the step, available to later steps as `body`.

## Reading input data

Every entry of **Data to use in the code** is a key of `inputData`. A value that is exactly one variable keeps its type: a number stays a number, a record stays an object, a list stays an array.

<CodeGroup>
```javascript JavaScript
const email = inputData.email;
const items = inputData.items;
return { domain: email.split('@')[1], count: items.length };
```

```python Python
email = inputData['email']
items = inputData['items']
return {'domain': email.split('@')[1], 'count': len(items)}
```
</CodeGroup>

## Returning a result

Return any JSON-compatible value: an object, a list, a string, a number or a boolean. Later steps reference it through the variable menu as `body`, or a field of it. A thrown error or a raised exception fails the step, and the message appears in the run details and in **Test your step**.

## Calling APIs with `fetch`

> **Applies to:** 1.2.0 and later

Both languages offer `fetch(url, options)`. It sends an HTTP request and returns a response object. In JavaScript you `await` it; in Python it is a plain call.

<CodeGroup>
```javascript JavaScript
const res = await fetch('https://api.example.com/v1/contacts', {
  method: 'POST',
  headers: { 'X-Request-Source': 'softr' },
  body: { email: inputData.email, name: inputData.name },
});
if (!res.ok) {
  throw new Error(`Contact API answered ${res.status}: ${await res.text()}`);
}
return await res.json();
```

```python Python
res = fetch('https://api.example.com/v1/contacts', {
    'method': 'POST',
    'headers': {'X-Request-Source': 'softr'},
    'body': {'email': inputData['email'], 'name': inputData['name']},
})
if not res.ok:
    raise RuntimeError(f'Contact API answered {res.status}: {res.text()}')
return res.json()
```
</CodeGroup>

**Options**

| Option | Meaning |
|---|---|
| `method` | `GET` by default; `POST`, `PUT`, `PATCH`, `DELETE` and the others work as expected. |
| `headers` | An object of header names and values. |
| `body` | A string is sent as it is. An object or a list is sent as JSON with `Content-Type: application/json`. In JavaScript, `URLSearchParams` is sent form-encoded. |
| `integration` | The alias of an attached integration that should authenticate this call. Needed only when two attached integrations share a host. |

**Response**

| Member | Meaning |
|---|---|
| `status`, `ok` | The HTTP status code, and whether it is in the 200 range. |
| `headers` | The response headers with lower-case names. JavaScript: `res.headers.get('content-type')`. Python: `res.headers['content-type']`. |
| `text()`, `json()` | The body as text or parsed JSON. In JavaScript both are `await`ed. |
| `arrayBuffer()` (JavaScript), `bytes()` (Python) | The raw body, for binary answers. |

### Letting an integration authenticate the call

Attach the integrations your code talks to under **Integrations the code can call**. When the code calls a URL on the API host of an attached integration, the request carries that integration's credentials automatically. The code never sees a token, and nothing you paste into the code is needed.

<CodeGroup>
```javascript JavaScript
// "salesforce" is attached to the step; the call to its API host is authenticated for you.
const res = await fetch(`${inputData.instanceUrl}/services/data/v60.0/sobjects/Account`, {
  method: 'POST',
  body: { Name: inputData.companyName },
});
return { created: res.ok, account: await res.json() };
```

```python Python
# Two attached integrations share the host api.hubapi.com; the alias picks the one to use.
res = fetch('https://api.hubapi.com/crm/v3/objects/contacts', {
    'method': 'POST',
    'body': {'properties': {'email': inputData['email']}},
    'integration': 'sales_hubspot',
})
return res.json()
```
</CodeGroup>

- The credentials are only added when the URL points at the provider's own API host. A call to any other host goes out without them, whatever alias you pass.
- You can attach every integration the **Call API** action can authenticate with. Database connections, Softr Databases, Softr Apps, Telegram and Trello cannot be attached, because their credentials have no HTTP header form.
- An alias is a short name of letters, digits and underscores, unique within the step. It defaults to the integration type, such as `salesforce` or `rest_api`.
- A REST API integration has no provider host, so it never authenticates a call by host alone. Name its alias in the call, and its headers go to whatever host that call names.

<Warning>Do not put API keys or tokens into the code or into **Data to use in the code**. Connect the service as an integration and attach it to the step instead. The credential then stays out of your workflow definition and out of the run details.</Warning>

### Calls without an integration

`fetch` also reaches any public host without an attached integration. The request is sent exactly as you wrote it, including any headers you set. Private networks, `localhost` and cloud metadata addresses are blocked.

## Calling HTTP APIs with `http` and `https`

> **Applies to:** 1.0.0, 1.1.0
>
> **Version history**
> - Removed in 1.2.0. Use [`fetch`](#calling-apis-with-fetch) instead.

JavaScript can call HTTP APIs with the Node.js `http` and `https` modules. Return the promise of the result; the step waits for it.

```javascript
return new Promise((resolve, reject) => {
  const url = 'https://api.example.com/v1/contacts?email=' + encodeURIComponent(inputData.email);
  const req = https.request(url, { headers: { Authorization: 'Bearer ' + inputData.apiToken } }, (res) => {
    let data = '';
    res.on('data', (chunk) => (data += chunk));
    res.on('end', () => resolve(JSON.parse(data)));
  });
  req.on('error', reject);
  req.end();
});
```

Python code has no network access in these versions. In JavaScript, `localhost` and the cloud metadata addresses are blocked.

## Cryptography

Both languages come with a cryptography module. The code can hash values, compute and check HMAC signatures, and decrypt or verify data that a partner encrypted or signed with RSA.

### JavaScript: `crypto` and `Buffer`

> **Version history**
> - Added to 1.0.0 and 1.1.0 in September 2026.

`crypto` is the Node.js `crypto` module: `createHash`, `createHmac`, `privateDecrypt`, `publicEncrypt`, `sign`, `verify`, `randomUUID` and the rest of it. `Buffer` converts between text, base64, hex and raw bytes.

```javascript
const decrypted = crypto.privateDecrypt(
  { key: inputData.privateKeyPem, padding: crypto.constants.RSA_PKCS1_PADDING },
  Buffer.from(inputData.encryptedToken, 'base64'),
);
const signature = crypto.createHmac('sha256', inputData.signingSecret).update(inputData.payload).digest('hex');
return { token: decrypted.toString('utf8'), signature };
```

### Python: `rsa`

> **Version history**
> - Added to 1.0.0 and 1.1.0 in September 2026.

`import rsa` gives you the API of the `rsa` package: `rsa.PrivateKey.load_pkcs1` and `rsa.PublicKey.load_pkcs1` read a PEM or DER key in PKCS#1 or PKCS#8 form, `rsa.decrypt` and `rsa.verify` accept the ciphertext or signature as base64 text or as bytes, and `rsa.encrypt`, `rsa.sign`, `rsa.DecryptionError` and `rsa.VerificationError` work as in the package. Padding is PKCS#1 v1.5.

```python
import rsa
key = rsa.PrivateKey.load_pkcs1(inputData['privateKeyPem'])
token = rsa.decrypt(inputData['encryptedToken'], key).decode()
return {'token': token}
```

<Warning>Keep private keys and secrets out of the code. Pass them in through **Data to use in the code**, mapped from a place only the right people can read, such as a record in a table with restricted access. The code then stays readable, and the same key is not repeated in every step that needs it.</Warning>

## When something fails

- A **script error** fails the step with the message of the error or exception. Test the step to see it while you write the code.
- A **`fetch` error** (1.2.0 and later) is raised as an exception in your code, so you can catch it. Its message names the reason: a blocked host, an unknown alias, too many calls, or a target that did not answer.
- **Execution timed out**, **Async script timed out** and **Memory limit exceeded** name the limit the run hit. Split the work between steps, or narrow the data the step receives.

## Versions

Steps created with an earlier version of Run Custom Code keep working. Opening such a step in the workflow editor upgrades it to the current version; code that used `http` or `https` must switch to `fetch` then. The **Applies to** line at the top of this page names the versions the page covers. An **Applies to** line under a heading names the versions that section applies to; without one, a section applies to every version of the page. A **Version history** block under a heading lists what changed for that part.

| Version | What changed |
|---|---|
| 1.2.0 | `fetch` in both languages, and the integrations attached to the step authenticate the calls. Node.js 24 and Python 3.12. Class definitions and many more standard modules in Python, top-level `await` in JavaScript, about two minutes per run. `http` and `https` removed. |
| 1.1.0 | The same inputs and runtime as 1.0.0. |
| 1.0.0 | The first version. |
