An integration is an external service connected to a workspace. You connect it once, and then any app, block, or workflow in that workspace can use it. Most of the ones you will browse here hold data — an Airtable base, a Google Sheet, a Notion database, a monday.com board, a Supabase project — and those are the workspace's **data sources**.

These six tools let an assistant explore what's connected, find the exact table it needs, and look at a few of its real records. They are all read-only. They exist to answer "what data is available here, and what does it look like?" so the answer can be used somewhere else: wiring a table to a [vibe coding block](/mcp/vibe-coding), or filling in a [workflow step](/mcp/workflows) that reads from Airtable.

<Note>
  **A data source is a kind of integration, not another word for one.** Every data source is an integration; the reverse is not true. Gmail, Slack and OpenAI are integrations with no records in them, so there is nothing to browse inside them and they are not data sources.

  `integration_list` lists everything the workspace has connected and says which entries hold data. The other `integration_list_*` tools browse inside those. Either word gets you to the right place — the assistant works out which you mean.
</Note>

## Browsing is a drill-down

These tools are one path, not six separate features. Each level needs an ID from the level above, so the assistant walks down from the workspace to the fields of one table, and then to a sample of its records.

```
integration_list                          workspace
└── integration_list_databases             a base, spreadsheet, doc, workspace, or database
    └── integration_list_schemas           only some integrations have this level
        └── integration_list_tables        a table, sheet, board, or list
            ├── integration_list_table_fields   its fields
            └── integration_get_sample_records  a few of its real records
```

| Tool | What it does |
|---|---|
| `integration_list` | Lists the integrations connected to a workspace |
| `integration_list_databases` | Lists the top level inside one integration — bases, spreadsheets, docs, workspaces, projects, or databases |
| `integration_list_schemas` | Lists the middle level, for the integrations that have one |
| `integration_list_tables` | Lists the tables, sheets, boards, or lists |
| `integration_list_table_fields` | Lists a table's fields, their types, and how to reference them |
| `integration_get_sample_records` | Reads the first records of a table, with the distinct values each field holds in that sample |

### Some integrations have a middle level

Most go straight from the top level to tables. Seven have something in between, so browsing them takes five steps instead of four:

| Integrations | The middle level is |
|---|---|
| Supabase, PostgreSQL, SQL Server, Snowflake | a SQL schema |
| BigQuery | a dataset |
| SmartSuite | a solution |
| ClickUp | a space |

A SQL connection usually has just one database — for Supabase it is called `postgres`.

For everything else, skip `integration_list_schemas` and go straight from databases to tables. Calling it on an integration that has no middle level returns an error rather than an empty list, so that "no schemas" is never mistaken for a fact about your data.

<Warning>
  **MySQL, MariaDB and Xano look like they belong in the table above, and don't.** They treat the schema and the database as the same thing, so they have nothing to browse in between — list their tables directly.
</Warning>

## Which integrations are supported

Every data source type Softr supports can be browsed and connected to a block through MCP:

| Kind | Integrations |
|---|---|
| Softr's own | Softr Databases — though [the database tools](/mcp/databases) do much more |
| Spreadsheets and docs | Airtable, Google Sheets, Microsoft Excel, Notion, Coda |
| Project and work tools | monday.com, SmartSuite, ClickUp |
| CRMs | HubSpot, Salesforce, Zoho CRM |
| SQL databases | Supabase, PostgreSQL, MySQL, MariaDB, SQL Server, Snowflake, Xano, BigQuery |
| Custom | REST API |

Each has its own setup guide in the **Data Sources** section of these docs. Connect it to the workspace there first, and it becomes browsable through MCP.

<Note>
  If an integration you expect is missing from a result, check that it is connected to the workspace you are asking about rather than a different one. If a table is missing, check you are looking under the right top-level entry — a monday.com board only appears under the monday.com workspace that owns it.
</Note>

## Referencing fields in code

`integration_list_table_fields` returns each field's type and options, the table's primary field, and one thing that matters more than it looks: how fields must be referenced in code.

| Integrations | Fields are referenced by |
|---|---|
| Softr Databases, SmartSuite, ClickUp, monday.com, Coda, HubSpot, Salesforce, Zoho CRM | **ID** |
| Everything else — Airtable, Google Sheets, Excel, Notion, BigQuery, REST API, and every SQL database | **Name** |

Rather than memorising that table, read `fieldReferenceKey` from the response: it says `"id"` or `"name"` for the table you just looked at. For SQL databases the two are the same string anyway, because a column's ID *is* its name.

<Warning>
  Getting this wrong fails silently. Code using the wrong form compiles, saves, and looks correct in the builder — and then returns nothing when the page loads. If a block renders but its data is empty, this is the first thing to check.
</Warning>

## Reading real values before building

A field list says a column is called `Status` and holds text. It does not say whether the values are `open` and `sold` or `Open` and `Sold`, which roles your users table actually contains, how dates are written in a sheet, or which tab of a spreadsheet holds the data. An assistant that builds without knowing produces an app that saves `"Sold"` into a source that only accepts `"sold"`, or user groups for roles nobody has.

`integration_get_sample_records` closes that gap. Given the same IDs as `integration_list_table_fields` plus the app being built, it returns:

| Part of the response | What it holds |
|---|---|
| `records` | The first records of the table — 20 by default, up to 100 — each with its ID and its field values, keyed the way `fieldReferenceKey` says. Text longer than 500 characters is cut. |
| `valueSummary` | For every field, the distinct values seen in those records (at most 20, in the order they first appear), how many records left it empty, and whether there were more values than fit. Fields whose values are objects — attachments, linked records — are marked `complex`; read those from `records` instead. |
| `fields` | Every field of the table with its ID, name, type, and the reference to use, so a narrower follow-up call can name just the columns it cares about. |
| `totalCount` | How many records the table has, when the source reports it. |

The assistant can pass `fields` to read only some columns and `limit` to read more rows — the usual way to learn all the options of a status column is to ask for that one field with a higher limit.

<Note>
  **It is a sample, not a query.** Everything in the response comes from the records that were read; a value missing from the sample may still exist further down the table. For searching and filtering, connect the table to the app and query it from there, or use [the database tools](/mcp/databases) when the table is a Softr Database.
</Note>

Two things to know about how it reads:

- **It reads through an app.** The tool takes an application ID because Softr reads external data on behalf of an app, not of a workspace. For a [vibe coding app](/mcp/vibe-coding) that is the app being built; create it first. The same read is what the app will use once the table is connected, so nothing is done twice.
- **The first read of a new table may need a retry.** For Airtable, Google Sheets, Notion and the other synced sources, the first time any Softr app reads a table Softr starts syncing it. A small table finishes within the call; a large one may not, and the tool answers with a conflict asking the assistant to retry in about ten seconds. SQL sources such as Supabase are read live and do not have this step.

The sample is available with **Applications & Forms: Read only** access to the app's workspace, plus the integration being connected to that workspace. It supports every integration in the table above except Softr Databases, which have [their own record tools](/mcp/databases).
